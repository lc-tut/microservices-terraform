02. LC-Cloudとは

そもそも、LC-Cloudって何？

LinuxClub（サークル）が自分たちで運営している、プライベートなクラウド基盤です。サークルのサービスやメンバーのプロジェクトを動かすための「土地」だと思ってください。この基盤自体も、誰かが手作業で設定しているのではなく、このリポジトリのコード（Terraform）で管理されています。AWSやGCPのような既製のクラウドを借りるのではなく、サークル自身がインフラを持っているからこそ、その中身をコードごと覗いて学ぶことができます。

Authentik

誰が入会していて、どのチームに所属しているかを管理するIdP。入会フォームの送信からアカウント発行まで、この仕組みの上で動いています。

GitHub

サークルのOrganization・チーム構成・誰が何を承認できるかを管理。すべての変更はPull Requestを通ります。

Harbor

各プロジェクトが使うコンテナイメージを保管する倉庫。脆弱性スキャンも自動で行われます。

OpenStack

VM・ネットワーク・ストレージなど、実際にプログラムが動く場所そのものを提供します。

02. LC-Cloudとは

なぜ自分たちでクラウドを作るのか

サービスを動かす基盤が要る

サークル運営のWebサービスやツールは、誰かのPCの中ではなく、いつでも動き続ける場所が必要です。その置き場所を、他社のクラウドに頼らず自分たちで持っています。

本物の運用経験を積める

権限管理・コスト管理・障害対応まで含めて自分たちで設計・運用することで、教科書には載っていない「実際の現場で起きること」を体験できます。

すべてコードで残る

設定や手順を誰か一人の頭の中に頼ると、その人がいなくなった瞬間に運用が止まります。Gitに残すことで、誰でも経緯を追える状態を保っています。

つまりLC-Cloudは、サークル運営のためであると同時に、みなさんにとっての「本物のインフラに触れる練習場」でもあります。

03. 基礎知識

クラウド・仮想マシンの基礎

1台の物理サーバーを、ソフトウェアの力で複数台の「仮想的なコンピュータ」に分割して使うのが基本アイデアです。この「分割して貸し出す」仕組みがあるからこそ、1台の物理マシンを何十人ものユーザーで無駄なく共有できます。

物理サーバー

ハイパーバイザー

物理サーバーの中身を複数のVMに切り分けるソフトウェア

VM（仮想マシン）

切り分けられた1つ1つの「仮想的なコンピュータ」。普通のPCのように使える

03. 基礎知識

APIの基礎

API（Application Programming Interface）は、あるプログラムが別のプログラムの機能を、決まった形式で呼び出すための「窓口」です。今回みなさんが作るのは、まさに「APIを叩いてVMを操作するUI」です。

リクエスト

「VMを起動して」のように、こちらから送る要求。何をしてほしいかを決まった形式で伝えます。

エンドポイント

リクエストの送り先となるURL。機能ごとに別々のエンドポイントが用意されているのが普通です。

レスポンス

結果として返ってくるデータ。多くはJSON形式で、成功したか・何が起きたかが書かれています。

料理店で考えると: メニュー（決まったAPI）を指して注文すると、厨房（サーバー側）が作って皿（レスポンス）を返してくる、という関係です。

03. 基礎知識

HTTPメソッド：動詞を使い分ける

Web APIの多くはHTTPという通信規格の上に成り立っています。「何をしたいか」は、URLだけでなくメソッド（動詞）でも表現します。

メソッド意味例
GETデータを取得する。何も変更しないGET /todos
POST新しいデータを作るPOST /todos
PATCH既存データの一部だけ書き換えるPATCH /todos/3
DELETEデータを削除するDELETE /todos/3

同じURL（例: /todos/3）でも、メソッドが違えば意味が変わります。今回のVM操作でも、一覧の取得はGET、起動・停止の指示はPOSTになります。

03. 基礎知識

ステータスコード：結果を数字で伝える

レスポンスには必ず3桁の数字（ステータスコード）が付きます。中身を読まなくても、大まかな結果がこの数字だけでわかります。

コード意味
200 OK成功（主にGET）
201 Created新規作成に成功した
202 Accepted受け付けたが、処理はこれから（非同期）
400 Bad Requestリクエストの中身がおかしい
401 Unauthorizedそもそも誰か分からない（未ログイン・トークン不正）
403 Forbidden誰かは分かるが、その操作をする権限がない
404 Not Found指定したURLの対象が存在しない
500 Server Errorサーバー側の不具合

401と403は混同しがちですが、区別しておくと後で楽になります。「JWTが無い/壊れている(401)」のか「JWTは正しいがその操作の権限がない(403)」のかで、UI側に出すエラーメッセージも変わってきます。

03. 基礎知識

実際にAPIを叩いてみると

抽象的な話だけだとイメージしづらいので、シンプルな例で見てみましょう。「やることリスト（todo）」を管理するAPIがあるとします。

POST /todos
Content-Type: application/json

{ "title": "資料を読む" }

↓

201 Created
{ "id": 42, "title": "資料を読む", "done": false }

エンドポイント（/todos）・メソッド（POST）・ボディ（JSON）・ステータスコード（201）。この4点セットがAPIの基本文法です。今回のMiddleware APIも、対象がtodoからVMに変わるだけで、考え方はまったく同じです。

03. 基礎知識

Infrastructure as Code（IaC）とは

従来はWeb画面をポチポチ操作してサーバーを作っていました。IaCは、その操作を「コード」として書き、実行することでインフラを再現できるようにする考え方です。

レビューできる

インフラの変更もアプリのコードと同じようにPull Requestでレビューしてからマージできるので、いきなり本番が壊れるリスクを減らせます。

履歴が残る

「いつ・誰が・何を変えたか」がGitの履歴としてそのまま残るので、後から原因を追いやすくなります。

再現できる

同じコードを実行すれば、同じ環境を何度でも作り直せます。手順書を見ながら手作業で再現する必要がありません。

03. 基礎知識

IaCのメリット・デメリット

メリット
  • 変更をPRでレビューできる
  • 「いつ・誰が・何を」変えたか履歴が残る
  • 同じ環境を何度でも再現できる
デメリット
  • ツール自体の学習コストがある
  • 最初にコード化する手間がかかる
  • コンソールを直接触る手軽さは失う

Keystone

OpenStackでできること（今のLC-Cloud）

OpenStack自体は非常に多機能ですが、LC-Cloudで実際に使えるのは今のところこの範囲です。

✓VM（Nova）起動・停止・一覧・削除
✓ネットワーク（Neutron）プロジェクトごとの仮想ネットワーク

フォルダごとに別々のState

Terraformは「今の実際の状態」をStateというファイルに記録します。LC-Cloudでは、フォルダ（スタック）ごとに別々のStateを持つ設計にしています。1つの巨大なStateにすべてをまとめることはしません。

影響範囲が狭まる

workspacesの誰か1人の変更ミスが、platform全体のStateを巻き込んで壊すことはありません。

applyが速い

1つのStateに含まれるリソース数が少ないほど、planやapplyにかかる時間も短くなります。

権限と1対1になる

「誰がこのStateをapplyできるか」を、フォルダ単位のCODEOWNERSでそのまま表現できます。

Stateの保存先（バックエンド）は、LC-Cloud自身の上で動くCeph RGW（S3互換のオブジェクトストレージ）です。PII（個人情報）はStateに含めない設計になっているため、State自体の暗号化は必須にしていません。

08. 今回のお題

Middleware APIの役割

「Middleware API」は実は1つのアプリではなく、役割ごとに分かれたinfra-api・billing-api・k8s-apiという3つのサービスの総称です。みなさんが使うのは主にinfra-api（OpenStack操作）です。3章で見たバックエンドの役割を、そのまま担っています。

① 認証はしない

「誰か」の確認はAuthentik Outpostに完全に任せます。infra-apiは、Ingressが付けてくれたヘッダーを信じるだけです

② 操作の代行

Vaultから取り出したApplication CredentialでOpenStack（Nova等）を呼び出します

③ 結果の整形

OpenStackから返ってきた複雑なレスポンスを、UIが使いやすいシンプルなJSONに変換して返します

08. 今回のお題

なぜMiddleware APIが必要なのか？

「UIから直接OpenStackを呼べばいいのでは」と思った人もいるはずです。それをしない理由があります。

秘密情報を守る

OpenStackを操作するApplication Credentialのような「鍵」をブラウザのJavaScriptに埋め込むと、誰でも盗み見できてしまいます。鍵はVault・サーバー側だけが持ちます

認証を自分で作らない

ログイン処理を自前実装せず、Ingressのforward-auth機能とAuthentikにまるごと任せることで、車輪の再発明をしていません

窓口をシンプルにできる

OpenStackの生のAPIは多機能で複雑ですが、infra-apiは「一覧」「起動」「停止」のような、必要な操作だけのシンプルな窓口を用意できます

この設計思想は一般的なWebアプリでも同じです。ブラウザ（フロントエンド）は秘密の鍵を持たず、バックエンドサーバーが代わりに外部サービスを呼ぶ、という形が基本です。

08. 今回のお題

infra-api 利用ガイド（実際の設計より）

これは想像ではなく、実際の設計文書に書かれているエンドポイントです。認証ヘッダーを自分で組み立てる必要はありません。

GET  /api/infra/me
GET  /api/infra/projects/{project}/vms
GET  /api/infra/projects/{project}/vms/{id}
POST /api/infra/projects/{project}/vms/{id}/start
POST /api/infra/projects/{project}/vms/{id}/stop
GET  /api/infra/projects/{project}/vms/{id}/console

{project}はチーム名ではなく、ワークスペース名（catalog/projects/の名前）です。/meは「自分が誰か」をヘッダーから読み取って返すだけのエンドポイントで、ログイン直後のユーザー名表示に使えます。VMのコンソールはnoVNC（ブラウザで動くVNCクライアント）をWebSocket経由で配信します。

08. 今回のお題

実装で気をつけたいこと：セッション切れ

Cookie認証には1つ落とし穴があります。セッションが切れると、fetch()は自動でログイン画面のHTMLを追いかけてしまい、ステータスは200のまま中身がJSONじゃなくなります。

async function apiFetch(path) {
  const res = await fetch(path, { credentials: "same-origin" });
  const type = res.headers.get("content-type") || "";

  if (!type.includes("application/json")) {
    // ログイン画面に飛ばされている = セッション切れ
    location.href = "/outpost.goauthentik.io/start?rd=" + location.href;
    return new Promise(() => {});
  }
  return res.json();
}

response.okだけを見るコードは、この「200なのに中身が違う」ケースを見逃します。Content-Typeまで確認するのが安全です。
